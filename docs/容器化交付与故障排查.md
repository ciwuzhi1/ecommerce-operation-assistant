## 2. 部署拓扑与启动顺序

### 2.1 服务与卷

七个 service 分三层，三个命名卷：

| 层 | service | 端口（宿主） | 命名卷 | 作用 |
|----|---------|-------------|--------|------|
| 基础层 | `mysql` | `127.0.0.1:${MYSQL_PORT:-3306}` | `mysql-data` | 业务库（MySQL 8.4） |
| 基础层 | `redis` | `127.0.0.1:${REDIS_PORT:-6379}` | — | 队列与缓存（Redis 7，不持久化） |
| 基础层 | `agent-checkpoints` | `127.0.0.1:${AGENT_POSTGRES_PORT:-5433}` | `checkpoint-data` | 智能体断点状态（PostgreSQL 16，库名 `agent_checkpoints`） |
| 应用层 | `api` | `${API_PORT:-8000}` | `api-uploads`（挂载 `/app/uploads`） | FastAPI：迁移 + HTTP |
| 工作层 | `worker` | — | `api-uploads`（同一份） | Celery 四队列 + Beat |
| 工作层 | `web` | `${WEB_PORT:-3000}` | — | Next.js 工作台 + BFF |

> 三个基础服务的宿主端口只绑定 `127.0.0.1`，供宿主侧排查与开发复用；生产环境如不需要，
> 可直接删掉对应 `ports:` 段（`api` / `web` 仍需对外暴露）。

### 2.2 启动顺序（全部由 healthcheck 驱动）

```
mysql(healthy) ─┐
redis(healthy) ─┼─→ api ── 先 alembic upgrade head，再 uvicorn ──(healthy)─┬─→ worker
agent-checkpoints(healthy) ─┘                                              └─→ web
```

关键点：

- **不靠 `sleep` 猜时间**：`depends_on` 全部使用 `condition: service_healthy`，前置服务探针通过才启动后继服务。
- **api 启动即迁移**：`api.command` 为 `sh -c "alembic upgrade head && exec uvicorn ..."`，迁移失败则 uvicorn 不启动，容器停在 unhealthy，不会带残缺表结构对外服务。
- **worker 等 api 健康**：确保 Worker 消费任务时业务表已经建好。
- **`exec` 接管 PID**：配合 `init: true`，SIGTERM 能正确转发，容器优雅退出。

### 2.3 健康检查一览

| service | 探针 | 判据 | interval / retries / start_period |
|---------|------|------|-----------------------------------|
| `mysql` | `mysqladmin ping` | 返回 `mysqld is alive` | 10s / 12 / 30s |
| `redis` | `redis-cli -a $REDIS_PASSWORD ping` | 输出含 `PONG` | 10s / 12 / 15s |
| `agent-checkpoints` | `pg_isready` | 退出码 0 | 10s / 12 / 20s |
| `api` | `GET /health`（urllib） | HTTP 200 | 10s / 12 / 40s |
| `worker` | `celery inspect ping` | 输出含 `pong` | 30s / 5 / 60s |
| `web` | `GET /login`（node fetch） | HTTP 2xx | 10s / 12 / 30s |

> `api` 的 `start_period: 40s` 是为了覆盖首次 `alembic upgrade head` 建 36 张表的耗时；
> 若目标机器磁盘很慢，先看 `docker compose logs api` 里迁移是否仍在进行，再判断是不是卡死。

### 2.4 Worker 队列与 Beat

`worker` 的 command 等价于：

```bash
celery -A app.worker.celery_app.celery_app worker \
  --loglevel=INFO \
  -Q generation,agent,agent.workflow,maintenance \
  -B --schedule=/tmp/celerybeat-schedule
```

- 四个队列与 `api/app/worker/celery_app.py` 的 `task_routes` 一一对应。
- `-B` 内嵌 Beat，周期任务（投递派发 5s、运行维护 30s）走维护队列，符合 DesignSpec §8「Beat 任务走维护队列」。
- `--schedule` 指向 `/tmp`：镜像以非 root 用户运行，`/app` 不可写，Beat 默认把 `celerybeat-schedule` 写在 CWD 会启动失败。
- **多副本注意**：`docker compose up -d --scale worker=3` 会拉起 3 个 Beat，周期任务被重复触发。
  维护类任务本身幂等（Outbox 幂等键 + 权属凭证），不会造成重复写入，但会浪费资源；
  若要正式扩容，应把 Beat 拆成独立 service（不在此次交付范围内）。

## 3. 中国大陆网络配置

### 3.1 方式一：Docker daemon 配 registry-mirrors（推荐，一次配好全局生效）

编辑 `/etc/docker/daemon.json`（Windows 为 Docker Desktop → Settings → Docker Engine）：

```json
{
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://dockerproxy.net"
  ]
}
```

改完重启 Docker daemon。配好后**普通镜像名（`mysql:8.4`）也会自动走镜像源**，
可以把 `docker-compose.yml` 里的镜像地址改回上游写法：

```bash
MYSQL_IMAGE=mysql:8.4
REDIS_IMAGE=redis:7-alpine
POSTGRES_IMAGE=postgres:16-alpine
NODE_IMAGE=node:22-slim
PYTHON_IMAGE=python:3.12-slim
UV_IMAGE=ghcr.io/astral-sh/uv:0.12.8
```

### 3.2 方式二：直接用镜像源前缀（当前默认）

`docker-compose.yml` 与两个 Dockerfile 已经把默认值写成国内可拉取的地址，
无需改 daemon 配置：

| 用途 | 默认值 | 覆盖变量 |
|------|--------|---------|
| MySQL | `docker.m.daocloud.io/library/mysql:8.4` | `MYSQL_IMAGE` |
| Redis | `docker.m.daocloud.io/library/redis:7-alpine` | `REDIS_IMAGE` |
| PostgreSQL | `docker.m.daocloud.io/library/postgres:16-alpine` | `POSTGRES_IMAGE` |
| Python | `docker.m.daocloud.io/library/python:3.12-slim` | `PYTHON_IMAGE` |
| uv | `docker.m.daocloud.io/astral-sh/uv:0.12.8` | `UV_IMAGE` |
| Node | `docker.m.daocloud.io/library/node:22-slim` | `NODE_IMAGE` |

### 3.3 依赖源（已在 Dockerfile 内置）

| 生态 | 默认源 | 覆盖方式 |
|------|--------|---------|
| Python (uv) | `https://pypi.tuna.tsinghua.edu.cn/simple` | `--build-arg PIP_INDEX_URL=...` |
| npm | `https://registry.npmmirror.com` | `--build-arg NPM_REGISTRY=...` |

npm 侧额外设置了 `replace-registry-host=always`：`package-lock.json` 里记录的是
`registry.npmjs.org` 的地址，不重写的话 `npm ci` 仍会回源到官方仓库。

## 4. 首次部署步骤

```bash
# 1) 准备根目录 .env（compose 从这里读取并注入容器，密钥不进镜像）
cp .env.example .env
#    必须修改：
#      APP_ENV=production           ← .env.example 默认给的是 development，不改则弱密钥校验不生效
#      MYSQL_ROOT_PASSWORD          ← 32 位以上随机串
#      REDIS_PASSWORD               ← 32 位以上随机串
#      AGENT_POSTGRES_PASSWORD      ← 16 位以上随机串
#      AUTH_SECRET_KEY              ← 32 位以上随机串
#      VIDEO_DURATION               ← .env.example 里的 2 不是合法时长，改成 5 或 10
#      NEXT_PUBLIC_API_BASE_URL     ← 浏览器实际能访问到的后端地址（改了 API_PORT 必须同步改）

# 2) 静态校验（不会拉镜像、不起容器）
docker compose config --quiet && echo "compose 配置合法"

# 3) 构建镜像
docker compose build

# 4) 起全栈（基础层 → api 迁移 → worker / web 自动按健康检查串行）
docker compose up -d

# 5) 观察健康状态，直到七个服务全部 healthy/running
docker compose ps

# 6) 初始化首个管理员（密码只经环境变量传入，不落库明文）
docker compose exec api python scripts/bootstrap_user.py   # 需先设置 BOOTSTRAP_* 变量，见 api/scripts/bootstrap_user.py
```

访问 `http://<宿主IP>:${WEB_PORT:-3000}`。

**弱密钥会被直接拒绝启动**：`APP_ENV=production` 时，`api/app/core/config.py` 会校验
`AUTH_SECRET_KEY`（≥32 位、非 `replace_with_` 前缀）与 `AGENT_CHECKPOINT_PASSWORD`（≥16 位），
不通过就抛错终止。compose 里 `${VAR:-...}` 的默认值全部是占位值，因此**带默认值上线一定起不来**——
这是有意设计，避免弱密钥被误用到生产。

## 5. 按现象定位边界的对照表

排查原则：**先确定故障落在哪一层，再进那一层**。下表把「现象」直接映射到「边界」和「第一条验证命令」。

| 现象 | 最可能的边界 | 第一条验证命令 |
|------|-------------|---------------|
| `docker compose up` 直接报 `required variable ... is missing` | 变量插值层：根 `.env` 缺失或键名拼错 | `docker compose config \| grep -n "<变量名>"` |
| 拉镜像超时 / `TLS handshake timeout` / `i/o timeout` | 网络层：镜像源不可达 | `docker pull docker.m.daocloud.io/library/mysql:8.4` |
| 构建时 `npm ci` 卡住或 404 | 网络层：npm 源 | 用 `--build-arg NPM_REGISTRY=https://registry.npmjs.org` 重试 |
| 构建时 `uv sync` 卡住或解析失败 | 网络层 / 依赖锁：PyPI 源或 `uv.lock` 与 `pyproject.toml` 不一致 | 用 `--build-arg PIP_INDEX_URL=...` 重试；确认 `uv.lock` 已提交 |
| `api` 容器反复重启，日志有 `AUTH_SECRET_KEY must be set to a strong value` | 配置层：弱密钥被应用拒绝 | `docker compose logs api \| tail -30` |
| `api` 起不来且日志停在 `alembic upgrade head` | 应用层·迁移：MySQL 不可达或迁移脚本冲突 | `docker compose exec mysql mysqladmin ping -uroot -p` |
| `api` healthy 但接口 500，日志有 `pymysql.err.OperationalError` | 应用层·数据库连接：库名/密码/端口不一致 | `docker compose exec api python -c "import os;print(os.environ['DATABASE_URL'])"` |
| `api` 启动报 `Invalid AGENT_CHECKPOINT_DATABASE_URL` 或连接 PostgreSQL 超时 | 应用层·断点库 | `docker compose exec agent-checkpoints pg_isready -U agent -d agent_checkpoints` |
| 智能体运行报 `AGENT_LEASE_LOST` / 任务一直 `queued` 不执行 | 工作层·投递：Worker 没起或 Beat 没跑 | `docker compose logs worker \| grep -i beat`；`docker compose exec redis redis-cli -a "$REDIS_PASSWORD" llen maintenance` |
| `worker` 一直 unhealthy | 工作层·Worker：进程没起来或 broker 不可达 | `docker compose logs worker \| tail -50` |
| Worker 日志有 `Permission denied: 'celerybeat-schedule'` | 工作层·权限：`--schedule` 没指到可写目录 | 检查 `worker.command` 是否含 `--schedule=/tmp/celerybeat-schedule` |
| 素材生成成功但图片 404 | 存储层·共享卷：`api-uploads` 未挂载或属主不对 | `docker compose exec api ls -ln /app/uploads`（属主应为 10001） |
| `web` 页面能开但列表全空 / 500 | 边界：前端 BFF ↔ api 内网连通性 | `docker compose exec web node -e "fetch('http://api:8000/health').then(r=>console.log(r.status))"` |
| 浏览器控制台请求 `127.0.0.1:8000` 失败 | 边界：构建期烘焙的 `NEXT_PUBLIC_API_BASE_URL` 与访问方式不匹配 | 该值在 `web` 构建期固定，改完必须 `docker compose build web` 重建 |
| 登录 401 / 令牌无效 | 应用层·认证：`AUTH_SECRET_KEY` 变更导致旧令牌失效 | 重新登录；确认 `AUTH_SECRET_KEY` 未在两次部署间改动 |
| 上传/生成报磁盘满 | 存储层：日志或上传卷写满 | `docker compose exec api df -h /app/uploads` |
| 迁移报 `Target database is not up to date` | 应用层·迁移：多副本并发迁移或历史版本分叉 | `docker compose exec api alembic current`、`alembic history` |

## 6. 标准排查顺序

固定按「五步」走，**不要跳步**，每步都留下一条证据再进入下一步。

### 第 1 步：确认是「配置问题」还是「运行问题」

```bash
docker compose config --quiet && echo "compose 配置合法"
docker compose config | grep -E "image:|published:|condition:" | head -40
```

- 配置阶段就报错 → 问题在 `.env` 与变量插值，先解决，不要往下走。
- 配置合法 → 进入第 2 步。

### 第 2 步：看「谁不健康」，而不是「谁报错」

```bash
docker compose ps
```

按健康状态把服务分成三类：

| 状态 | 含义 | 下一步 |
|------|------|--------|
| `healthy` | 探针通过 | 跳过 |
| `unhealthy` | 容器在跑但探针失败 | 进第 3 步看该服务日志 |
| `starting` | 仍在 `start_period` 内 | 等待，不要急着下结论 |
| `exited` / `restarting` | 进程已死或被重启策略拉起 | 进第 3 步看该服务日志 |

**关键判据**：只要 `mysql` / `redis` / `agent-checkpoints` 里有任何一个不是 `healthy`，
`api` 就永远不会启动——此时问题一定在基础层，跟应用代码无关。

### 第 3 步：读日志，按「启动顺序」自下而上

```bash
docker compose logs --tail=100 mysql
docker compose logs --tail=100 redis
docker compose logs --tail=100 agent-checkpoints
docker compose logs --tail=100 api      # 重点看 alembic 是否跑完、有没有弱密钥报错
docker compose logs --tail=100 worker   # 重点看有没有 "ready"、Beat 是否启动
docker compose logs --tail=100 web
```

自下而上的理由：上层服务的报错绝大多数是下层没就绪的**派生现象**，
先修下层可以避免在错误的层里改代码。

### 第 4 步：在容器内复现，确认是「边界不通」还是「逻辑不对」

```bash
# api → mysql
docker compose exec api python -c "import pymysql,os,urllib.parse as u; p=u.urlparse(os.environ['DATABASE_URL']); pymysql.connect(host=p.hostname,port=p.port,user=p.username,password=p.password,database=p.path[1:]).close(); print('mysql OK')"

# api → redis
docker compose exec api python -c "import os,redis; redis.from_url(os.environ['REDIS_URL']).ping(); print('redis OK')"

# api → postgres（断点库）
docker compose exec api python -c "import psycopg,os; psycopg.connect(host='agent-checkpoints',port=5432,user=os.environ['AGENT_CHECKPOINT_USER'],password=os.environ['AGENT_CHECKPOINT_PASSWORD'],dbname=os.environ['AGENT_CHECKPOINT_DATABASE']).close(); print('pg OK')"

# web → api（内网）
docker compose exec web node -e "fetch('http://api:8000/health').then(r=>console.log('api',r.status))"

# 浏览器 → api（外网，注意这条走的是宿主端口，与上一条不同）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:${API_PORT:-8000}/health
```

三条内网探针全通、外网 `curl` 也通 → 边界没问题，问题在业务逻辑，回到应用层日志定位。

### 第 5 步：需要重建时，按「最小代价」顺序尝试

```bash
docker compose up -d --force-recreate api worker   # 只重建应用层，不动数据卷
docker compose build --no-cache api && docker compose up -d api   # 依赖装坏了才用
docker compose down                                  # 停栈，保留命名卷
# ⚠️ docker compose down -v 会删除三个命名卷（业务数据 + 断点状态 + 上传素材），
#    属于不可逆操作，执行前必须先备份。
```

**绝对不要**为了排查方便执行 `docker compose down -v`。

## 7. 数据卷、备份与迁移

### 7.1 三个命名卷

| 卷 | 实际名称 | 内容 | 丢了会怎样 |
|----|---------|------|-----------|
| `mysql-data` | `ecommerce-operation-assistant_mysql-data` | 全部业务数据 | 业务数据全丢，需重新初始化 |
| `checkpoint-data` | `ecommerce-operation-assistant_checkpoint-data` | 智能体断点状态 | 挂起中的审批无法恢复，运行需重跑 |
| `api-uploads` | `ecommerce-operation-assistant_api-uploads` | 上传素材与生成产物 | 素材文件丢失，记录中的 URL 变死链 |

### 7.2 从旧卷名 `agent-checkpoint-data` 迁移

早期版本的 `docker-compose.yml` 把断点状态卷命名为 `agent-checkpoint-data`，
本次按 DesignSpec §4 统一为 `checkpoint-data`。**直接 `up` 会得到一个空的断点库**，
已挂起的审批会丢失。迁移步骤：

```bash
docker compose down
docker volume create ecommerce-operation-assistant_checkpoint-data
docker run --rm \
  -v ecommerce-operation-assistant_agent-checkpoint-data:/from:ro \
  -v ecommerce-operation-assistant_checkpoint-data:/to \
  alpine sh -c "cp -a /from/. /to/"
docker compose up -d
```

如果不需要保留历史断点状态（开发/演示环境），直接 `up` 即可，PostgreSQL 会自动初始化空库。

### 7.3 备份

```bash
docker compose exec -T mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --databases "$MYSQL_DATABASE"' > backup-mysql.sql
docker compose exec -T agent-checkpoints sh -c 'exec pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-checkpoint.sql
docker run --rm -v ecommerce-operation-assistant_api-uploads:/data -v "$PWD":/backup alpine tar czf /backup/backup-uploads.tar.gz -C /data .
```

## 9. 环境隔离：开发 vs 生产

两套环境**不能混用**，混用最典型的后果是：开发机把数据写进容器库、或生产误连开发的外部实例。

| 维度 | 开发环境 | 生产环境（本文件） |
|------|---------|-------------------|
| 编排 | 本机进程（uvicorn + next dev + celery） | Docker Compose 七服务 |
| MySQL | 复用外部实例 `:13306` | 容器 `mysql:3306` + `mysql-data` 卷 |
| Redis | 复用外部实例 `:6379` | 容器 `redis:6379`（无卷） |
| PostgreSQL | 复用外部实例 `:5432`，库名 `agent_checkpoints` | 容器 `agent-checkpoints:5432` + `checkpoint-data` 卷 |
| 密钥 | `api/.env` 本地文件 | 环境变量注入（根 `.env` → compose） |
| 迁移 | 手动 `alembic upgrade head` | api 容器启动时自动执行 |

开发环境**必须使用独立数据库名 `agent_checkpoints`**（DesignSpec §4 环境隔离要求），
避免与其他项目数据混杂。

## 10. 已知取舍与未覆盖项

| 项 | 现状 | 原因 / 后续 |
|----|------|------------|
| `APP_ENV` 默认 `production` | compose 默认生产语义 | 与根 `.env.example` 的 `development` 不同，部署时必须显式设置，否则弱密钥校验不生效 |
| compose 内保留占位密钥默认值 | `${VAR:-replace_with_...}` | 为了让 `docker compose config` 在没有 `.env` 时也能通过静态校验；占位值会被生产校验拒绝，不会真的上线 |
| Worker 与 Beat 同进程（`-B`） | 与 DesignSpec §4 图示一致 | 多副本会重复触发 Beat；维护任务幂等所以不产生重复写入，正式扩容应拆分 Beat 为独立 service |
| `web` 未使用 Next.js `output: "standalone"` | 运行层复制 `.next` + 生产 `node_modules` | 避免改动 `web/next.config.ts`（有其他工作线在改）；standalone 可进一步缩小镜像，属于后续优化 |
| `web` 运行层未复制 `next.config.ts` | 生产构建产物已烘焙 | 现有配置只含 `allowedDevOrigins`（仅开发生效），生产行为一致；若后续加入 `redirects`/`headers` 等运行时配置，必须补拷该文件 |
| 基础服务宿主端口仍发布 | 只绑 `127.0.0.1` | 兼容 README 的开发复用流程；生产可删掉 `ports:` 段 |
| Redis 不挂数据卷 | 队列允许丢失 | DesignSpec §1：Redis 做队列，可靠性由 Outbox + 幂等键保证，不依赖 Redis 持久化 |
| 未做 Compose `deploy.resources` 限额 | 未设置 CPU / 内存上限 | 目标机器规格未定（DesignSpec §11 待明确事项）；确定后按 Worker 副本数补 |
| 未验证真实 `docker compose up` | 只做静态校验 | 本任务明确要求不启动容器；第 8.2 节列出了上线前必须实跑通过的项 |
